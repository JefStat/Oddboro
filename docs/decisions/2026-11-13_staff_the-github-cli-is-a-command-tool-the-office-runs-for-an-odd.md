- [staff] **Decision (2026-11-13): the GitHub CLI is a command tool. The office runs `gh` for an Odd, outside the Odd's sandbox, on the owner's GitHub sign-in. The Odd gets `gh_read` and `gh_write`, and never the token.** An Odd's shell hides every secret (2026-11-04), so `gh` there has no sign-in, and a token in its environment would reach its transcript and the ledger. A connector of kind `command` (`cli: 'gh'`, `signInFrom: 'github'`) is a catalog tool like GitHub (`GH_ID` in `packages/ledger/src/registry.ts`), granted at read or write on the Access tab. `upstream` returns an in-memory MCP client (`ghClient`), so the gateway holds, ask-first and standing yes (2026-11-10) work with no change. `gh_read` has `readOnlyHint` and runs only the listed read commands (`READS` in `gh-args.ts`). `gh_write` runs every other command, and at Draft each call waits on the desk with its exact arguments. A read grant gets `gh_read` only. The token comes from `bearer('github')` at call time, goes into the child's `GH_TOKEN` alone, and is cut from the output. The child gets a new empty home and `GH_CONFIG_DIR`, so the owner's own `gh` login is never used. Output sits inside `<untrusted>` tags. The office refuses, for both tools, `gh auth`, `config`, `alias`, `extension`, `browse`, `codespace`, the key commands, `gist create`, `release create`, and any flag or `@value` that reads a file of this computer (`--input`, `--body-file`, `-F`, `--field`). The sign-in is the GitHub tool's, with scopes `repo read:org read:user`, so a command that needs more is refused by GitHub. The owner installs `gh`. Code in `apps/office/src/lib/server/gh-tool.ts` and `gh-args.ts`.
